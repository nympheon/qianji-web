# 钱迹 Android 4.5.4 同步、请求与登录逻辑复核

- 日期：2026-10-18
- 样本：`qianji_454_1234_gw.apk`，`com.mutangtech.qianji`，4.5.4 / 1234
- 方法：通过用户提供的 MT MCP 对同一只读工作区检查方法、调用者和 Smali；未登录、未请求钱迹业务服务器、未修改 APK
- 证据范围：客户端实现；不据此宣称服务端仲裁、幂等或令牌续期已验证

## 1. 同步入口需要分开

| 路径 | 观察到的实际行为 | 本项目应采用的规则 |
| --- | --- | --- |
| `Lch/c.startSync(Context, false)` | 检查距上次完成是否不足 5000ms、是否已同步中及是否已登录；经 `Lch/c$c$a.invokeSuspend` 先同步标签，再同步账单 | 普通刷新合并同一任务，不建立各页面独立同步器 |
| `Lch/c.startSync(Context, true)` | 跳过 5 秒判断；此参数还传入账单拉取器，不只是“忽略缓存” | 不能把页面“立即增量刷新”直接映射成此参数 |
| `Leh/a.start(Context, true, callback)` | 将本轮起始 `lasttimes` 置空，按全量路径拉取 | 首次、明确全量重建才使用清游标语义 |
| `Lch/c.startPush(Context)` → `Lch/c$b$a.invokeSuspend` | 只调用上传器 `Lgh/a.start`，没有先拉标签或账单 | 普通账单保存不强制先拉全域，也不每次保存后追加完整同步 |
| `Lch/c.h(Context, boolean)` | 调用账单拉取器，随后调用上传器 | 完整同步编排和保存后的只上传是两条调用链，不能混为一谈 |

60 秒新鲜期、跨网页和 MCP 共享任务是本服务已确认的适配策略，并非 APK 定时器。保留普通增量入口 5 秒完成后冷却；页面普通手动增量刷新也可遵循它。全量重建的显式操作可以使用 APK 的强制路径，但仍合并并发请求。没有依据为这些入口增加空闲轮询。

## 2. 账单拉取是逐页应用、结束保存游标

`Leh/a.pullNewDataInner` 请求 `/syncv2/pull`，解析成 `Leh/c`，立即调用 `dbhelper/m.savePullResult` 保存本页，再返回 `pageParams`。该页的分类、修改记录与删除记录进入本地库，具体替换语义见[冲突分析](2026-10-18-apk-conflict-analysis.md)。

`Leh/a.start` 的循环：

1. 本轮沿用固定的起始 `lasttimes`，每页传递上次回执的分页参数。
2. 将各页返回的 `lastSyncTimes` 汇入本轮结果。
3. 只有观察到 `hasMore=false` 的正常结束，才调用 `c(JsonObject)` 保存新 `syncbook_times_`；失败不推进它。
4. 存在 200 次拉取的保护分支。达到边界不应被本服务当作完整同步成功；Worker 执行分片也不能重置上限后无限循环。
5. 首次或强制全量路径，页间有 150–220ms 随机等待；普通增量并非一律插入此等待。

这不支持“APK 在全轮成功前保持所有新记录不可见”的说法。本项目普通增量可用 D1 按页事务应用数据、同步进度和本地修订号，整轮结束再保存成功游标。无需为了模仿 APK 建设每条记录的历史代次数据库。查询必须说明正在同步或同步不完整；要求完整统计时等待整轮完成。全量重建使用临时数据集以便失败时继续使用原数据，是服务端实现适配，不是 APK 的固有规则。

## 3. 标签不是普通账单游标，也不只是旧版 list

`Ldh/c.b()` → `network/api/tag/a.syncAll` → `/tag/syncall`：

- 请求参数为 `uid`、`lasttime`、`page`，page 从 0 起；本轮 `lasttime` 固定。
- `lasttime` 来自 `Lab/a.getTimeUser("tags_sync_time")`。
- 每页解析 `Lfh/a`，调用 `dbhelper/d0.savePullResult`；使用其 `hasMore` 继续，处理相应标签与分组变化。
- 正常结束调用 `Lab/a.recordTimeUser`。该方法实际记录 `System.currentTimeMillis()`，是本地毫秒时间，不是服务器返回的账单游标。
- `Ldh/c.start` 的 boolean 参数没有在本轮已检查的方法中改变此游标；重新构建标签需要显式清理其独立游标。
- 循环上限为 40 页。达到上限仍会进入记录时间的公共尾部，这是应验证的客户端边界，不能在本服务中把未拉完的结果静默标为完整。

实现时沿用已确认的请求字段与单位，分别保存“协议要求的标签 lasttime”和“服务的数据新鲜时间”。本地时钟与服务端窗口是否会漏掉同步期间发生的标签变化，仍需实际契约验证；不把本地时间擅自换成账单的服务端游标，也不宣称已解决该窗口。

## 4. 请求构造与重试

`Lbl/c` 两种构造方式都在有登录 UID 时加入 `fr`：

| 构造方式 | 身份头 |
| --- | --- |
| `build()` → `d(Lql/c)` | 当前 `utoken`，以及显式指定的其他头 |
| `buildSyncStringRequest()` → `e(Lsa/e)` | `htoken: 1`、当前 `utoken`，以及显式头 |

所以 `htoken` 应根据各操作实际使用的请求构造器登记，不能猜一个“所有账务写接口”名单统一加头。标签 `syncall` 使用后者；普通登录和刷新令牌使用前者。

`Lbl/c.params(name, null)` 会移除参数；`paramsIfNotEmpty` 跳过空字符串。省略、空值、零和负一各自有语义，不用通用清空规则替换。

`Lsa/a.c` 默认向 `d` 传 20000ms；`d` 和同步请求 `e` 都构造 `DefaultRetryPolicy(timeout, 0, 1.0)`，此处自动重试次数为零。同步接口可以由调用者指定超时，应逐操作记录。此前设计统一给只读请求最多三次尝试没有 APK 依据，改为默认不自动重试；用户下一次请求可以重新开始可安全读取的任务，当前在途任务可恢复尚未请求的页。恢复不能把写请求重新执行，尤其不能重发切换式接口。

`Lsa/a` 和 `JNIHelper` 的 native 签名仍需单独完成可移植算法核验；不能因以上 Java 请求层已读清楚，就假定旧参考项目签名完全有效。

## 5. 登录、状态失效和线路

- `network/api/account/a.login` 发送 `v` 和经 `Lza/h.e` 处理的 `pwd`，使用普通请求构造器。密码处理算法的实现与测试向量仍须核对，不能以字段名代替验证。
- `account/a.refreshToken` 存在，发送 `uid`；本轮 dispatch 交叉引用结果没有直接调用者。因此自动刷新不能描述成 APK 已有成熟行为，也不能保证凭 UID 可以恢复已失效的 token。服务管理保留重新登录；手动令牌刷新在完成真实验证后启用，不做后台续期。
- `Lsa/b.c` 先调用全局拦截器。经 `Ldb/f.k` 注册的 `Ldb/c` 转入 `Ldb/f.l`：当外层 `ec=8888` 且 `em` 中的 `code=40005` 时清理登录关联状态并调用 `logout`；`code=40009` 则打开客户端专门的限制提示。两者不是所有网络异常的统称。
- `Lsa/b` 另将 `-9000` 用于网络不可用、`-9001` 用于空结果/服务器异常等本地错误。应保留原始业务码与必要说明，区分重新登录、网络、协议和官方限制。
- `Lkb/b.getCurrentHost` 优先采用用户已选线路，否则使用配置/默认线路；没有在该路径发现超时自动轮换线路。沿用明确选择，避免一次写超时后换线路重发。

本项目不会因 APK 登出逻辑就删除本地操作记录和账务副本；保留它们用于断线查询及结果核查，是运行在 Worker 上所需的恢复设计。

## 6. 保留的 Worker 适配与尚未证实事项

保留：同一协调器、持久写键与发送状态、结果不明只核查、无损 ID/金额、按页事务、完整性标记、全量重建的数据集切换。它们分别解决并发 HTTP、重启、alarm 重投递及 JavaScript 数字精度，与 APK 业务规则不冲突。

不新增：通用三方合并弹窗、每笔写前全域同步、每笔写后全域回拉、所有查询自动三次重试、空闲轮询、Worker 周期出账。

仍需真实验证：服务端多端仲裁、ID 拒绝的完整条件、标签本地时间窗口、刷新令牌有效条件、部分接受与异常回执。没有账号和测试数据的情况下，本轮只做证据核对，不以伪造请求补齐这些结论。
