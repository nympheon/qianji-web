# 钱迹 Android 4.5.4 业务逻辑复核汇总

- 日期：2026-10-18
- 样本：用户提供的 `qianji_454_1234_gw.apk`，包名 `com.mutangtech.qianji`，4.5.4 / 1234
- 目的：重新检查本项目设计中涉及账务、关联、同步及状态转换的假设，优先采用 APK 已有规则，减少自创逻辑和不必要请求
- 产出：[修订后的主设计](../superpowers/specs/2026-10-18-qianji-workers-design.md)
- 边界：本轮为只读静态审查，没有登录、真实业务写入或产品代码实现；覆盖当前设计中的各业务领域，不表示 APK 的每个方法、所有 native 算法和服务端行为均已验证

## 1. 采用原则

1. **业务语义以当前 APK 实际调用链为先。**同时查看请求参数、表单前提、模型计算、成功回调及关联更新，不以 API 名称或旧项目常量替代证据。
2. **官方可完成的业务不再拆成 Web 自建操作。**例如差额记账、退款、报销、周期出账、储蓄关联转账，优先用对应官方用例及回执。
3. **Worker 只增加运行环境必需的保护。**持久写键、发送状态、并发协调、结果不明核查和 JavaScript 无损数字有明确用途；不增加全局三方合并、空闲轮询或第二套计划执行器。
4. **疑似缺陷不照抄，接口存在不等于功能已可用。**可确定的规则落实到设计；静态缺口继续补查；仅服务器能回答的内容保留真实验收任务。

## 3. 已落实的修订

| 检查项 | APK 证据及修订后的规则 |
| --- | --- |
| 普通账单写前刷新 | `startPush` 是只上传路径。去掉每笔写入必先拉最新目标的通用规定；有依赖、过期或缺失才补取 |
| 写后核验 | 完整账单组/资产/预算回执直接应用；只有缺字段或结果不明等需要时补读，不固定追加完整同步 |
| 增量保存 | 普通增量按页事务落库、整轮末保存成功游标；移除所有记录的历史代次发布机制 |
| 查询完整性 | 逐页模式下明确正在同步/未完整，完整统计等待结束；本地分页绑定修订号，变化后要求重查 |
| 全量重建 | 与普通手动增量刷新分开。APK 强制参数不仅跳过 5 秒冷却，也清空账单起始游标 |
| 请求节奏 | 保留普通冷却、并发合并及全量页间短暂停顿；60 秒缓存仍为用户确认的服务策略，无空闲定时请求 |
| 标签同步 | 使用新版 `/tag/syncall` 的独立 `lasttime/page` 与分组变化；不只依赖旧 `list` 或套用账单游标 |
| 分页截断 | 不把页数保护触发或未完成结果当完整成功；标签本地时间窗口和40页尾部分支单独验证 |
| 身份头 | 逐操作按 `build` / `buildSyncStringRequest` 登记 `utoken/htoken`，不把全部写操作归为一种请求 |
| 重试 | 请求层已查到零自动重试，移除自创统一三次读取重试；写入响应不明先核查 |
| 登录维护 | 区分明确业务失效、网络、协议及官方限制；未找到自动调用 refreshToken 的证据，不承诺自动续期 |
| 冲突 | 普通下发自动替换，`conf_ids` 对应客户端 ID 重分配；不用它推导编辑版本冲突或服务端胜出规则 |
| 金额 | 区分输入价、保存主额、资产额和统计值；优惠已扣入保存值，统计不得再扣一次 |
| 币种 | 保留 src/target/base 历史值、匹配顺序及费用换算；不以现汇重算，不擅自统一中间舍入 |
| 收支汇总 | 共用原生逐类型槽位模型；退款、报销、转账、还款、优惠不按名称直接归为普通收入/支出 |
| 跨期退款/报销 | 补载源账单关联的跨期子记录，净额归源期间/分类；历史源期间缓存一起失效 |
| 新旧报销 | 保留旧字段与新映射的优先级和兼容区别；取消报销保留待报销类型，不自动执行账户升级 |
| 批量报销 | 按源账单时间升序分配，末笔接金额及三币种余数，不自创平均分摊 |
| 组合报销22 | 已定位为按 packid 聚合真实21成员的虚拟显示行；不生成正式ID、上送或重复统计，修改/删除展开真实成员 |
| 退款前提 | 采用原生类型、25次新增入口与已有退款禁止改类型的限制；不臆造全局超额限制 |
| 关联删除 | 删除退款/已报销或源账单要处理关系、子记录及资产；不当作删除数据库一行 |
| 本地资产 | 沿用 APK 的新增、编辑回滚与新额应用算法作预期核验；官方返回完整资产时不再重复加减 |
| 转账与信用卡还款 | 两资产必须存在、不同且非借贷；费用及历史 targetValue 决定两侧金额，编辑按资产 ID 合并回滚和新额；lastPayTime 不随删除自动回退 |
| 借贷偿还 | 追加、本金偿还与利息按类型和实际 ID 字段分派；超余额输入拆本金/利息，资金侧只变一次总额；两笔进入同一同步容器但不能承诺原子接受 |
| 差额记账 | 修改余额时可以不记差额，选择记账则随资产提交传 `diffparams`；不用 Worker 另造第二笔调整账单 |
| 借贷汇总 | 统一识别资产和 listloan 同一对象，type6 包装项不重复计入；方向、符号、incount 与信用卡分期配置生效 |
| 结清 | 与还款分开，保留撤销结清；无明确目标参数的 finish 按可能翻转动作处理，结果不明不重发 |
| 预算 | 原生日期及账本 range 进入缓存键，修改使用回执预算配置；执行进度复用本地账单模型及独立预算标记 |
| 分类与标签 | 分类使用原生层级/移动/删除检查/迁移；删标签组保留标签，归档不清除账单引用 |
| 账本 | 退出与删除分开，保留 owner/member、过期及未结事项；单人服务不抹掉官方共享账本业务规则 |
| 周期执行 | 本地 Bill 构造链是预览；正式账单来自官方回执/同步，不建 Worker 出账或历史补账器 |
| 周期日期 | 月末32、29+/30+和法定调休沿用；缺官方节假日年数据不假装普通工作周等价 |
| 分期 | 已有分期配置边界为已确认的 incount/feeincount；保留首末期费用、尾差与新增初始次数，提前还款独立 |
| 翻转动作 | toggle/bindbill/finish 等对外表达明确目标状态，已满足目标则不调用；超时核查，避免重发后反转 |
| 储蓄 | 计算计划不是真实存入；存入可选关联转账，撤销按 transid 并核查关联账单；删除计划有 deleteBills |
| ID | 所有 ID 以字符串保留，但只对整数 ID 要求十进制；planid/transid 不强制数字，管理 ID、packId 与 billId 分开 |
| 附件 | 按需取得官方上传凭证，成功取得对象 key 后才能关联；沿用凭证余量和配置上限，基础方案不要求 R2 |

## 4. 保留的差异及理由

以下没有强行照搬 Android 实现：

- 单协调器与持久操作记录用于多 HTTP 调用、实例回收及重复任务投递；不能仅用 Android 式进程内锁。
- 未确认写入保留状态与本地预期，避免 MCP 将网络中断说成失败并诱发重复；这不是上游新增的幂等承诺。
- D1 有限事务、完整性状态、本地分页修订和全量临时集合用于服务端查询及恢复，不要求普通增量历史数据库。
- ID 和金额无损处理适应 JavaScript；计算中的显式舍入仍对照 APK，而非直接复制二进制浮点误差。
- 账号失效时保留本地数据、草稿和操作历史；只读核查所需证据不能随 token 一起丢弃。

## 5. 仍需要验证的事项

1. **协议实现：**native 签名的 Workers 可移植算法、画像与测试向量，逐接口编码、省略/清空语义、真实回执结构。
2. **服务端规则：**多端修改/删除仲裁、ID 拒绝全条件、翻转接口的云端语义和并发行为、部分接受与响应丢失后查回。
3. **计划执行：**全部手机离线、服务闲置时的周期/分期实际出账与时区，任务次数、提前还款及历史修改边界。
4. **历史兼容：**旧报销迁移、异常源子关系或意外云端type22、超额退款/报销及排除标记组合、币种覆盖不足和合法月底配置。组合报销的正常虚拟展示链已静态确认。
5. **疑似缺陷或非活跃入口：**提前还款 `images` 的疑似错误载荷、标签超页后记录时间、random 创建入口及 resetCount 的直接调用缺失。先核对，不把不确定分支当完整功能。
6. **外部兼容：**Cloudflare 出口各线路、令牌刷新有效条件、官方图片上传区/CORS/清理，以及当前账号权益和共享账本可写性。

这些验证按具体操作与状态转换推进；不能以普通新增账单成功、模拟测试或接口可见性，代替全部业务验收。
