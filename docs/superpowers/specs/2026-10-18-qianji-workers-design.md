# 钱迹个人网页版与 MCP 服务设计

- 日期：2026-10-18
- 状态：用户已于2026-10-18明确“使用这个设计”；已批准；更新计划及主代理顺序实现、最终独立审查已确认，开发中
- 修订：完成 APK 业务及缓存交叉复核；采用 Workers Paid 与单 SQLite DO，明确本地优先、按需校验、回执局部更新及恢复边界
- 目标客户端：钱迹 Android 4.5.4，versionCode 1234
- 已批准部署方案：Cloudflare Workers Paid + Static Assets + 一个 SQLite-backed Durable Object，数据库与领域协调同处，不单独引入 D1

## 1. 目标与已确认约束

为一个人提供完整的钱迹网页版和可接入 ChatGPT 的远程 MCP 服务。网页与 MCP 共用业务规则、数据副本、钱迹连接和同步任务，尽量覆盖 APK 中适合这两种交互方式的账务功能。

用户已确认：

1. 只有一个服务使用者、一个当前连接的钱迹账号，不建设多用户注册、租户或权限体系。
2. 应用页面和 MCP 均不增加访问认证，不建设 PAT、OAuth、一次性连接票据；入口保护由用户配置 Cloudflare。
3. 钱迹登录仅支持手机号或邮箱加密码，不实现微信、Apple 等第三方登录。
4. 提供完整网页版；MCP 与网页具有对应的业务能力，但交互组织分别适配自然语言和页面操作。
5. 完整功能和可靠性优先；用户允许采用 Workers Paid 来简化实现及提高运行余量，不强求 Free。数据库使用 Cloudflare 提供的服务，优先利用套餐包含额度；本轮具体存储推荐见第4节，不将先前的D1选型当作不可更改的业务需求。
6. 使用时按需更新。闲置且没有用户发起的在途任务时，不向钱迹发起请求，不做周期性后台轮询。
7. 普通查询使用 60 秒数据新鲜期；同步任务共享、合并。60 秒为本服务已确认的默认值，不是从 APK 得出的常量。
8. 保留登录、线路选择、登录状态维护、手动同步和同步诊断等必要服务管理功能。
9. 不复制 APK 的系统及个性化设置，不提供数据导出；排除手机专属能力与不适合本项目的账户管理功能。
10. 前端使用CSS库和组件库美化，具体选型已授权自行决定；采用Tailwind CSS、shadcn/ui及Lucide，详见第9节与开发计划。

成功标准：用户可以在网页或 ChatGPT 中查询、分析并管理钱迹数据；网页、MCP 和官方客户端的账务结果一致；跨设备变化能在使用时获取；并发调用、任务中断和网络异常不会产生重复记账或虚假的成功结果。

## 4. 架构与模块职责

| 模块 | 职责 | 边界 |
| --- | --- | --- |
| 网页 | React、TypeScript、Vite、Tailwind CSS 与 shadcn/ui 构建的中文响应式应用，通过 Workers Static Assets 发布 | 使用业务 HTTP API，不直接持有或请求钱迹 token |
| HTTP API | Worker 提供页面查询、操作、连接和任务状态入口，调用对象内用例 | 负责输入输出转换，不重复实现账务规则 |
| MCP | Worker 的 `/mcp` 提供无状态 Streamable HTTP、工具说明、结构化结果和任务状态 | 业务调用同一个对象；业务状态不依赖单个 HTTP 会话 |
| 领域服务 | 在对象内组织账单、资料、资产债务、预算统计、周期分期、储蓄、附件模块 | 网页和 MCP 共用用例及校验；不暴露任意 SQL 或任意上游路径代理 |
| 钱迹适配器 | 在对象内集中执行签名、画像、编码、无损 JSON、响应及错误归一化 | 版本更新不蔓延到页面和工具；上游变更沿用同一顺序控制 |
| 单个协调器 | 一个固定名称的 SQLite Durable Object，管理同步合并、写入次序、设备、签名及任务 | 按需唤醒，不建设多账号对象分片；本地查询不排在长网络请求后等待 |
| 对象内 SQLite | 当前数据副本、资料、操作日志、任务、游标、原始字段和连接配置 | 数据与领域逻辑同处；钱迹云端为账务权威来源，不另外复制一份到D1 |

所有动态业务经同一个对象，操作、数据及进度使用同库事务，省去DO与D1的存储衔接。协调器仍需明确管理跨网络 `await` 的队列和恢复状态，不能把单线程当跨请求互斥，也不能仅保存进程内Promise/Map。SQLite事务不跨钱迹请求；发送前与回执后分别提交持久状态。SQL游标在下一次await前消费完，金额和ID继续按无损文本处理。

本地缓存查询与任务状态读取不进入上游变更队列；同步页应用和写用例按既定边界串行。`blockConcurrencyWhile` 只用于必要的短初始化，不包住20秒上游等待或整轮同步。SQL迁移以schema_version和顺序脚本管理，使用SQLite DO官方事务/恢复能力，不新增产品内数据库管理或导出界面。

默认不引入 Cron、Queues、Workflows、常驻 WebSocket 或另一台服务器。用户发起的长同步允许通过持久任务及按需alarm续跑，任务记录和必要续跑安排持久化后才返回“进行中”。一个对象的alarm服务所有在途任务；仅在没有待续跑任务时取消。alarm可能重复执行，恢复先核对持久状态，不能因此重复提交钱迹写请求，也不能把waitUntil视作客户端离开后无限存活的保证。

图片上传首先沿用钱迹的上传与存储机制，不把图片二进制存入SQLite。若上游协议确需中转暂存，再增加R2并记录用途、生命周期和费用；R2不是基础方案的强制依赖。

### 4.1 套餐、存储与性能取舍

生产推荐 Workers Paid；当前账号最低每月5美元，具体用量超过包含额度时另计。[官方价格](https://developers.cloudflare.com/workers/platform/pricing/) 普通Worker的Free 10ms CPU与50次子请求预算较紧，Paid提供更大余量；该差异不等于上游网络变快，10ms也不能直接拿来描述DO限制。SQLite DO在Free也可用，减少组件来自同处计算与存储，Paid主要减少入口预算和每日数据库硬额度造成的约束。[Workers限制](https://developers.cloudflare.com/workers/platform/limits/)、[DO价格](https://developers.cloudflare.com/durable-objects/platform/pricing/)

单 SQLite DO 比“D1+协调DO”少一套数据库访问和状态衔接，更接近APK本地数据库/同步器的结构，适合本项目单人场景；代价是需要少量SQL版本迁移，所有动态业务经同一个对象。D1自带外部查询和迁移等工具，当前需求不依赖这些工具，不为未来可能需要而同时保留两套数据库实现。

性能提升目前是减少数据库往返与共享计算的架构判断，需用真实数据测量。Free和Paid的普通Worker内存都为128MB；查询、关联补载和统计采用有界读取、索引及修订号缓存，不一次性装载整库。Paid不消除任务检查点、上游调用限制、签名可移植性或远端结果不明。

选型比较、现行额度与费用演算见[Cloudflare最终选型复核](../../research/2026-10-18-cloudflare-paid-final-review.md)。本次只更新设计，不执行套餐开通或部署。

## 5. 登录、凭证和线路

1. 网页服务管理入口接收手机号或邮箱及密码，依照核对后的 APK 协议完成当次登录。密码及可重放的密码摘要均不持久化，不进入 MCP 参数或日志。
2. 保存 UID、稳定设备 ID、必要用户配置及加密 token。加密密钥来自 Worker Secret；部署更新和实例重启后仍能恢复连接。
3. 同一UID重新登录保留数据副本、设备ID、逻辑连接代次和操作记录，更新token；凭证更新不等于账号重绑。返回不同UID时不得混入旧数据，需显式切换连接及重建缓存；旧操作日志不随缓存删除。登录、退出和线路变更也进入连接变更的顺序控制；在途写未核清时先处理核查，不凭新token继续发送旧账号载荷。
4. 登录状态检查、手动刷新和普通调用复用同一状态机：已连接、检查中、需重新登录、协议异常、网络异常。网络或签名失败不能一律误报“密码失效”。
5. 令牌刷新先完成协议及实测验证；本轮未发现 APK 自动调用刷新接口的证据，因此不承诺自动续期。页面“更新登录状态”先采用已验证的状态读取；手动令牌刷新通过实测后启用，明确失效时重新登录，不为了保活定时请求。
6. 任何写操作若存在“钱迹可能已收到”的情况，登录刷新后也先核查操作结果，不直接重新提交。
7. 提供默认、备用、海外线路选择。默认使用已核对的主线，不后台自动测速或主动切线。用户点击测试时从 Worker 出口发起有限的只读检查。
8. 切线保留设备 ID、游标与操作记录；若线路不接受当前连接，明确提示重新登录，不清除已确认的账单数据，不重发结果不明的写操作。

页面与 MCP 的“免认证”指本服务的访问方式；连接钱迹账号是独立业务流程。Cloudflare 入口规则需允许 ChatGPT 的 MCP 请求通过，该连通性纳入验收。

## 6. 按需同步与数据完整性

### 6.1 触发和缓存

| 情形 | 行为 |
| --- | --- |
| 首次登录且没有副本 | 启动首次全量同步；页面显示进度，MCP 返回可查询的任务信息 |
| 打开网页或调用普通查询，相关域当前完整且最近完整同步不超过 60 秒 | 使用对象内SQLite，不为同一数据再发起上游同步 |
| 相关数据超过 60 秒 | 保留并可展示本地副本，合并到已有任务；账单/标签增量同步，其他资源只请求当前用例所需范围 |
| 统计/查询依赖全量完整性 | 等待整轮结束；若不能在请求期限内完成，返回任务状态，不能把半轮数据说成完整最新结果 |
| 多页面、多标签页或多个 MCP 并发调用 | 共享一个相关同步任务，不按调用次数复制上游请求 |
| 浏览器重新聚焦 | 检查相关数据新鲜度，遵循同一规则，不无条件刷新 |
| 用户明确要求增量刷新 | 绕过 60 秒缓存新鲜期，沿用增量游标与普通冷却，重复点击合并 |
| 用户明确要求全量重建 | 仅将该任务起始游标置空，保留当前集合的成功游标；进入独立全量任务，合并并发请求 |
| 写入后 | 采用该操作的官方回执与 APK 更新规则；重算受影响派生结果，缺失/不确定部分才针对性核查，不固定追加完整同步 |
| 闲置且无在途任务 | 不向钱迹请求，也不以保活、测速或令牌维护为由访问上游 |

网页可在任务进行时查询本服务的进度，这不触发另一轮钱迹同步。数据返回包含最近完整同步时间、当前修订号、正在同步/未完整状态和是否陈旧；页面可保留已显示结果并提示，MCP 必须传递相同的完整性与新鲜度信息。

普通账单同步入口继承 APK 已确认的 5 秒完成后冷却。60 秒缓存规则通常会减少触发次数；普通手动增量刷新也遵循该入口。APK 的强制入口同时跳过冷却并清空账单起始游标，只用于明确全量流程。写后核验为在途操作的一部分，由协调器安排，不让普通冷却把已发生的写入误判为失败。

账本、分类和成员优先采用初始化和同步下发的数据。用户资料、资产、预算、币种、周期、分期等域只在当前用例需要时补取；各域按明确查询范围的最近成功校验时间及失效标记控制缓存，不在每轮账单同步中刷新所有资源。普通在线查询仍以60秒作为默认远端检查新鲜期。完整回执已更新的对象不再仅因这次写入被强制回拉；失效区分派生结果需重算、源数据确需补取和结果待核查，不能一概清整域。切换式操作的前置状态读取绕过普通缓存，见第7节。

预算缓存键包含账本、日期筛选和原生 `range`。退款、报销及关联删除会影响源账单的历史期间、分类、预算和资产，失效范围不能只取子记录发生的当前月份。完整回执已包含的资源直接应用，不为使缓存失效而再次查询同一资源。

### 6.2 增量和完整性

- 首次/重建按核对后的协议从初始游标开始；普通轮次使用钱迹返回的按账本 `lasttimes`。分页回传真实 `bookid/pageoffset/pagesign`，不猜测或自行生成分页状态。
- 一轮账单同步固定起始 `lasttimes`，合并新增、修改、删除、分类变化。标签按 `/tag/syncall` 的独立 `lasttime/page` 协议处理标签与分组，不将其毫秒时间换成账单游标。各域独立标记完整时间。
- 普通增量采用当前记录表，按页用对象内SQLite有限事务原子应用本页变更、删除与进度；整轮正常结束再保存最终成功游标。失败保留已应用页和上次成功游标，重复页按业务ID收敛，不为每次增量维护全部记录的历史代次。
- 同步中或失败后的半轮结果明确标记为未完整；列表可显示已同步部分，完整统计和需要稳定全集的操作等待恢复完成。不能声称数据库仍保存一份完全不变的上轮快照。
- 本地分页令牌绑定账号、数据集、筛选和修订号；底层数据变化或重建切换后令牌失效，要求重新查询，避免把两次数据集合拼成一页。无需为令牌保留一整套历史记录。
- 全量重建使用临时数据集，原集合及其成功游标保留至新集合完整并在同库事务内切换；新集合不继承旧集合中未再次出现的记录。任务从首次上游请求至切换完成与本服务远端写入串行，跨alarm续跑仍保留边界；既有远端写请求结束或已转待核查后才启动。页面可读原集合、保存草稿并排队，切换后重新校验排队操作。操作日志与草稿不属于可替换数据集；允许只读重建参与结果核查，不要求必须先核清才能开始核查所需的重建，且不重发未知写。失败保留原集合与游标，这是为网页持续可用增加的有限适配。
- 可用的上游分页令牌按实际验证结果续用；若令牌失效，则从上一轮成功游标重新开始，不假定令牌无限期有效。沿用 APK 全量页间短暂停顿和分页保护，达到保护上限不冒充成功或无限续跑。
- 标签在所查 APK 中于结束时记录本地毫秒时间，40 页保护也进入该尾部；本服务仅在确认完整时推进成功状态，不照搬可能掩盖截断的行为。标签时间窗口仍列入真实验证。
- 完整同步后半段虽有APK的push步骤，本服务上传候选只取当前UID下持久操作状态明确为“尚未发送”或“收到明确ID冲突拒绝后可继续”的项目。已发送待核查、已成功、旧UID及仅因恢复仍呈脏状态的记录不自动再上传；读页恢复不等于写请求重放。
- 用户发起的在途任务在关闭页面后可以完成；它结束后不自行再安排下一轮同步。

### 6.3 与APK对照后的缓存分层

采用APK的本地优先展示、增量同步与回执更新，同时保留适合Web/MCP的共享任务和持久恢复。APK所查入口存在资产初始化1小时、资产选择器12小时、预算/周期/分期列表2小时的判断，并非统一短缓存；这些时长不直接搬到跨设备服务。当前60秒按需检查更能控制手机修改的可见延迟，但它不是后台周期或实时保证。证据、入口限定和取舍见[缓存与更新比较](../../research/2026-10-18-apk-cache-update-comparison.md)。

1. **当前副本不按TTL删除。** 60秒只决定下一次业务读取是否需要联系上游；网页可以先显示当前已确认记录及时间，再显示更新结果。上游失败保留副本并标陈旧，MCP不把它说成最新。同步半轮不能重新计算并宣称完整统计，页面已有旧结果可继续显示并注明状态。
2. **源校验与本地计算分开。** 源缓存按UID、域和规范化查询范围组织；有效空集合也保存完整获取标记。筛选列表的完整性只适用于其范围，不因空列表删除其他筛选或其他域资源；列表、详情、选择器共用实体记录。统计、日历、预算执行等按依赖数据修订、筛选、实际业务日期/范围、时区和币种缓存；源检查无变化时复用，不每60秒重算。跨日、跨账本周期或配置变化仍使相应结果失效。
3. **校验时间不滑动。** 记录明确范围的成功远端校验时间`validatedAt`与业务变化时间`changedAt`，读缓存不续期。账单协议游标、标签游标、数据revision各自保存。单条成功写入不能把全账号/整域校验时间刷新为现在；完整集合回执才能确认其覆盖范围。普通无变化同步只更新校验时间，不无故推进数据revision、使分页令牌失效或清统计缓存。
4. **回执驱动局部更新。** 按APK已核对规则更新源记录及关系，应用官方资产/预算/任务回执，失效其依赖结果；回执不完整或关系不明才补取。更新源历史期的退款/报销需失效相应历史统计；不能每笔写后统一刷新全部账单、资产和预算。
5. **慢读不能覆盖新写。** 在线资源读取记录其开始时的UID/连接代次、数据集与资源失效/写入代次，落库时复核；其间发生相关写入、失效或切换时，旧响应不覆盖已确认新值，也不清除待核查状态。必要时等待后续合并读取，不据此重发写请求。仅保存轻量代次，不引入记录历史版本库。
6. **入口只保留必要缓存。** 动态业务HTTP/MCP不放入CDN/Cache API，返回`Cache-Control: no-store`；浏览器内页面状态服从相同修订及新鲜度，不建立第二套持久账务副本或独立轮询。静态资源正常缓存，上传token及官方节假日资料按其已验证有效性处理，不套普通业务TTL。

## 7. 写入、同步收敛与结果核查

所有钱迹变更都由协调器执行，并持久化操作记录。操作状态包括：排队、发送中、核验中、已确认成功、已确认失败、结果待核查、部分成功。

普通同步按APK已确认行为自动应用回执和下发记录，不为每次变化增加通用三版本选择弹窗。SQLite当前副本与草稿、待提交操作分表保存；草稿和日志不因副本刷新或重建而丢失。已确认值与待提交预期有明确状态。两端修改的最终结果以官方回执和回拉为准，不能从客户端替换行为推导“最后提交必胜”。

1. 网页自动生成稳定 `requestId`；MCP写工具要求相同用途的请求键。唯一键使用原UID与requestId，请求和结果查询核对当前UID；同账号同键同参数返回既有结果，同键不同参数拒绝执行，不能命中其他UID的同名写键。
2. 记录原UID、连接代次、目标、原始版本、计划变更及必要新ID，先持久化发送中状态，再访问钱迹。恢复及每次发送前核对操作仍属于当前连接；旧UID操作不得改绑新账号或用新凭证核查。
3. 同账号的同步应用与写入按序执行。普通账单沿用已取得的完整记录，应用明确的表单变更并保存待上传载荷，走 APK 的只上传路径；不为每笔保存固定增加一次全域或目标回拉。目标缺失、缓存失效、关联操作要求检查时才补取必要数据。版本用于保留诊断；目标已删除、类型或关系变化使操作不再适用时保留草稿并说明原因。没有证据承诺上游条件写入或跨设备强一致锁。
4. 核对 HTTP、业务错误码和回执中的逐项接受、拒绝及删除结果，按 APK 规则应用结果。完整资源回执直接更新；仅 ID 确认的账单按已核对的同步状态处理；需要补充字段、关联结果或核查不确定性时再针对性读取。核查范围包括账本、金额、时间、分类、资产、关系和扩展字段，不以每次全量回拉替代理解回执。
5. 明确业务拒绝可记录失败；网络中断、进程重启、缺失回执、回拉超时或字段不符均不能自动视为未执行。
6. 结果待核查时只做读取核验。可查询、刷新和处理无关数据；对相同目标及其关联数据的后续变更暂缓，避免扩大不确定性。
7. 批量操作记录逐项状态，已确认成功项不会因其他项失败而重发；钱迹不支持远端事务时，不承诺整批回滚。
8. 不根据金额、备注相同就自动合并或删除账单；重复候选只是辅助信息。写键负责请求重放，业务查重负责提示，二者分开。
9. 删除采用各领域原生的检查和关联处置：带退款/报销的源账单按 APK 处理子记录和资产回滚；分类有子项先处理子项，并使用 `deletecheckv2/deletev2` 的删除或迁移策略；删除标签组保留组内标签；资产采用自身检查，退出共享账本与删除账本分开。网页展示影响，MCP 提供准确注解和参数；不设计跨全部资源的通用级联开关，已明确的请求不增加无意义确认。
10. 报销迁移等账号级不可逆变化不自动触发；如当前业务必须执行，先呈现具体影响，由用户明确决定。
11. 将切换式接口包装为明确意图，例如暂停/恢复、绑定/解绑、结清/撤销结清、归档/恢复。在队列实际执行时按需读取上游当前状态，绕过普通60秒缓存；无法取得可靠状态则不发切换。绑定比较目标的具体packId，不能只问“是否已绑定”。已满足目标不调用，否则仅发一次；回执未含可证明目标达成的状态时进行针对性核查，业务成功不直接等于目标成功。这不构成跨设备条件写入保证；结果不明不自动重试。

实际录入按钱迹确认结果回填 UI。保留待核查状态和操作入口，不以页面乐观更新或 MCP 文本描述替代上游确认。

账单新建 ID 冲突单独处理：只有本次新增已收到明确拒绝回执、且其语义核对为 APK 对应的 ID 冲突时，才生成新 `billid` 并持久化尝试和 ID 映射，按有限批次继续上传；原 `requestId` 不变。不能给已有云端记录改 ID，也不能把编辑、删除失败或网络超时一律改成新建。待提交记录之间的引用按已核对的关系更新，回拉时核验最终分配的 ID。APK 一轮最多 5 批、每批最多 200 条是已观察到的客户端上传边界；本服务使用持久任务限制每次处理量，并按逐项确认结果计算成功数量。

## 8. 数据模型与账务计算

### 8.1 持久化范围

| 数据集合 | 主要用途 |
| --- | --- |
| 连接与服务配置 | 单个当前 UID、加密凭证、设备 ID、线路、客户端协议版本 |
| 当前账单及关系 | 原始无损数据、规范化字段、业务 ID、数据集与修订号、退款/报销/转账/任务等关系 |
| 账本、分类、成员、标签 | 显示、筛选、业务引用、层级和对应同步状态 |
| 资产与债务、预算、币种 | 业务资料、缓存及计算依据，保留上游时间与权限信息 |
| 周期、分期、储蓄计划 | 官方任务和计划及其关联信息，不凭本地推测生成官方执行状态 |
| 附件引用 | 钱迹资源引用和必要元数据，不在SQLite保存图片二进制 |
| 同步任务、分页和数据集指针 | 完整性、逐页进度、中断恢复、成功游标与全量切换 |
| 操作、草稿与逐项结果 | 请求去重、陈旧草稿识别、ID 冲突尝试及映射、回执、回拉核验及异常核查 |
| 能力清单 | 每项读写的协议版本、证据级别、验收状态及可用原因 |

所有业务 ID 使用字符串保存及返回；APK 的整数 ID 使用无损十进制字符串，包含 `-1` 等特定值，不经 JavaScript `Number` 转换。储蓄计划及交易等上游字符串 ID 按原样保留，不强制其为纯数字，也不混同任务 ID、packId、账单 ID 和交易 ID。原始响应和嵌套扩展字段使用无损 JSON 解析与序列化，编辑只覆盖明确修改的字段，未知字段保持不变，不向网页或 MCP 暴露内部原始请求载荷。

金额和汇率保留十进制文本，使用精确十进制运算。经确认有固定尺度的统计金额可另存定标整数，SQL 仅在相同币种与尺度下聚合，禁止用浮点转换作为账务合计依据。超出已确认精度或金额范围的输入明确报错，不静默四舍五入。

APK 模型使用 `double`，部分算术经 BigDecimal helper，除法有 10 位 HALF_UP、结余有两位 HALF_UP 的显式舍入点；本服务使用精确数字保留载荷，同时按原生业务步骤核对舍入，不把所有中间值一律截成两位。区分录入金额、保存 `money`、资产实际金额及统计金额：例如无多币种的支出原价 100、优惠 -10，保存 `money=90/transfee=-10`，统计支出 90、优惠独立 10，不能再减一次优惠。

### 8.2 统计规则

- 默认使用 `Asia/Shanghai` 解释业务日期，这是本服务默认值；APK 使用设备 Calendar 时区。原始时间戳保持原值，日历、筛选和统计共用边界及账本自定义月起日，不擅自规定月底截断。
- 复用 APK `BillStatItem.fromBill → StatSet` 的逐记录槽位转换。普通支出含类型 0/10、普通收入 1/11；待报销、转账、还款、退款、已报销及利息等各按原生分支处理，不能直接 `SUM(money)`。
- 转账与信用卡还款本金独立列示，正手续费参与总支出；负优惠单列，不能再成为收入或重复扣款。退款/已报销子记录不直接变普通收入。
- 统计源账单时按 ID 补载关联退款/报销子记录，不用主查询期间过滤子记录。普通支出一月 100、二月退款 30，一月净支出为 70，二月退款独立显示 30；源记录承担相应净额、期间与分类。
- 待报销尚未报销时本金不进总支出；新报销后按源金额、退款与已报销入账的残差形成支出或超额收入。旧字段、V2 映射及兼容 getter 分开；旧报销升级与异常分支仍需对照验收，不自动迁移。
- 多币种按账单保存的 src/target/base 符号与值、原生匹配优先级及手续费公式计算；不以现汇重写历史。缺少所需币种或关联记录时说明覆盖不足，不能把回退原值冒充任意币种精确换算。
- `FLAG_NOT_COUNT=1` 与 `FLAG_NOT_BUDGET=2` 独立；统计和预算复用同一逐记录模型并采用各自标记。转账本金不入预算、费用可入；子分类消耗可归父类，但总预算只累加一次。异常退款超额与排除标记组合按证据单独验证，不套全类型清零。
- 资产主列表与借贷明细按相同业务 ID 和 type/stype 识别同一对象；type6 汇总包装项不重复计入。借入/借出方向、符号截断、`incount`、信用卡是否包含分期均沿用 APK。历史趋势采用已核对的数据，不能从不完整账单推算。
- 未知类型及未知影响字段明确列示，不假定普通收支或零金额；详情见账单统计审查中的公式与边界向量。
- VIP、标签数、任务数和账本可写性采用当前账号和当前 APK 已核对的规则；不把参考项目自身常量直接视作官方限制。

### 8.3 关联业务的原生规则

- 退款使用 `refund2`，应用返回的整组账单及源子关系；本轮确认入口支持支出0和待报销5，新增入口达到25次退款时拒绝，已有退款的源账单不能任意切类型。不能自行新增普通收入代替退款，也不能臆造统一的“不许超本金”规则；真实约束逐项验收。
- 批量报销按源账单时间升序分配，末笔承接剩余金额及三币种余数。取消报销保留待报销类型，清理已报销关联并处理子账单/资产；取消报销与取消待报销属性是不同用例。
- 已定位列表链中的组合报销22是按 packid 组织真实21记录的虚拟显示对象，没有正式 billid，不落库或上送，也不重复统计。网页/MCP可返回分组及成员；批量修改/删除展开真实成员，不创建一笔类型22的云端账单。意外从云端收到22时单独核查，不据静态链断言它绝不会下发。
- APK 普通保存、退款编辑、删除等有本地资产增减算法，可移植为预期计算与核验契约；有 `inAsset` 等完整资产回执时以回执替换，不能又叠加一次本地增量。预期余额与上游已确认余额分别标识。
- 转账/信用卡还款要求两个不同且存在的非借贷资产。最终主额为 M、带符号费用为 F 时，转出额为 `M+max(F,0)`；转入额有历史币种值则取 targetValue，否则为 `M+max(-F,0)`。编辑先按资产 ID 合并旧额回滚与新额应用，再逐资产更新，防止方向交换或资产重叠重复计算。新增信用卡还款仅向前更新 lastPayTime，删除不自行回退它。
- 借贷走专用本金/利息用例：追加借入/借出为6/7，偿还/收回本金为9/4，利息另生成10/11；按 APK 债务字段映射及 LoanInfo 更新，不能所有类型一律把 assetid 当债务对象。超余额输入按原生表单拆本金和利息，实际资金一次变动二者合计，债务只变本金；两笔分别跟踪上送结果。此页面拒绝非本位币资金资产，不把普通跨币种转账能力泛化到借贷。删除本金与删除独立利息分开，不自创不存在的上游父子字段或直接归还 API。
- 资产余额变化沿用官方提交中的可选 `diffparams`；是否记差额由用户表达。存在未核清账单时先完成核查，不先改余额再由 Worker 另造差额账单。结清是独立状态动作，不等于还款或余额清零。
- 分类的层级调整、子分类移动及删除迁移使用官方专用动作；删除标签组令标签变为未分组，归档保留标签。账本 owner/member、过期及未结事项继续生效，不因本服务单人而绕过云端角色规则。
- 周期、分期本地生成的账单仅用于预览，正式账单采用官方回执与后续同步；不建立 Worker 自动出账或补历史期数。周期预览保留月末32、29+/30+及官方法定工作日语义，缺节假日数据时不偷偷退化为工作周。
- 分期保留本金/手续费的首末期分配与尾差模式，新增的已过期数按 APK 日期算法计算，不固定填0；已有对象仅开放确认过的配置，提前还款走独立接口并应用回执账单。预览 ID 不当正式账单 ID 上送。
- 储蓄的计划计算行与真实交易分开；存入可选同时关联转账，撤销按 `transid` 并核查关联账单删除，删计划明确 `deleteBills`。模式以实际创建入口为准，不因枚举里有 random 就宣称已支持。
- 图片按需获取官方上传 token，沿用到期前60秒安全余量；上传成功获得对象 key 后才能关联账单，图片数量读取当前配置。移除引用与销毁云端对象分开；后者需有已确认的官方协议。

## 9. MCP 与网页体验

### 9.1 MCP

工具按用户任务组织：连接状态与同步、基础资料查询和管理、账单查询与统计、各类账单写入、资产债务、预算、周期分期、储蓄计划、附件、操作核查。

- 查询参数、金额、ID、分页、筛选和错误在网页与 MCP 之间保持一致。
- 写工具使用明确业务 Schema，不设计万能 HTTP 请求工具。只读、变更和破坏性注解与实际行为一致。
- 返回结构化结果及简明文字，包含数据时间、任务或操作 ID、逐项结果和下一步核查方法。
- 缺少上游连接时返回服务管理页面地址；账号密码在网页录入，不要求模型收集凭证。
- 业务工具默认最多等待 10 秒；长同步或核验未在此期限完成时，以正常 MCP 工具结果返回进行中状态和任务/操作 ID，后续调用查询既有任务，不将超时包装成“操作失败，可以重试”。
- 提供能力与状态查询，服务器使用说明明确 ID 获取、分页、金额单位、写键复用和结果待核查处理。
- 普通 ChatGPT MCP 接入使用业务工具即可；不为此强制增加通用文档搜索或 ChatGPT 内嵌 UI。

### 9.2 网页

页面包括：总览、账单与日历、统计、资产与债务、预算、周期与分期、储蓄计划、账本/分类/标签管理、服务管理。

默认中文，桌面和手机浏览器均可用。共用账本、日期和业务筛选；展示新鲜度、正在更新、冲突、待核查及不可用能力的原因。无账号时进入连接流程，无数据时显示真实空状态，不默认混入演示账单。

用户已补充要求使用CSS库美化，并授权自行选型：采用Tailwind CSS 4.3稳定线、shadcn/ui官方组件与Lucide图标，具体兼容版本在开发时锁定。统一表格、筛选、表单、弹窗与状态反馈，核验手机布局和键盘可用性；CSS构建成静态资源，不增加运行时样式服务。具体组件和文件安排见开发计划。

服务管理只保留必要连接和诊断项目。普通业务配置放在对应业务页面，不建设 APK 全部设置的副本，也不把数据库、签名或内部任务术语塞进日常记账表单。

## 10. 异常与运行维护

稳定错误类别至少包括：登录被拒绝、需重新登录、网络异常、签名或协议异常、响应结构变化、账号权益不足、资源不可写、业务前置条件变化、ID 冲突处理失败、部分成功、结果待核查、同步失败、资源用量超限。ID 冲突、用户草稿与云端变化、结果不明分别建模，不能用一个笼统“冲突”错误替代。

上游请求沿用逐操作确认的超时与重试策略；所查 APK 请求层默认 20 秒、零自动重试，本服务也默认不自动重试，不凭空增加统一三次尝试。只读任务可在下一次使用或明确重试时恢复，未发送页可续跑；已发送写操作先核查。业务拒绝、签名错误和未知结构不重复请求，失败任务不持续安排访问。

日志使用操作 ID 和必要诊断字段，不记录密码、密码摘要、完整 token 或整份个人账单响应。连接失效、上游协议异常、待核查操作和同步失败通过当前页面与 MCP 状态返回，不另建消息通知系统。

代码、静态资源与数据库迁移可独立升级。迁移保留操作记录、稳定设备 ID 和当前数据集，避免部署重启触发无必要的全量拉取。运行维护文档包含 Cloudflare 绑定、Secret、迁移、部署、回滚、ChatGPT 连接及用量查看；付费开通、远程部署等外部变更按实际执行时的授权处理。

平台时间点恢复与普通实例重启分开：恢复前进入维护状态，恢复后的历史操作先核查钱迹现状再恢复写入，不能让回退的“未发送”状态自动重放历史操作。该流程属于运维，不增加公开恢复/任意SQL接口。

## 11. 验收标准

### 11.1 协议和数据正确性

1. 对照 4.5.4 的 Java/Smali 及必要 native 逻辑核对签名、客户端画像、设备 ID、身份头、编码、接口参数及响应模型，建立逐操作证据记录。
2. 覆盖长整数、嵌套数字、精确金额、未知字段、跨币种、账单关系、自定义周期及统计排除标记。
3. 验证跨账本分页、删除、分类与标签变化、重复页、失效分页令牌和断点恢复；增量失败不推进成功游标并标记未完整，全量重建失败仍可用原数据集，本地分页修订变化明确要求重查。
4. 模拟写入前后各阶段的超时和重启，证明重复调用同一写键或恢复不会重复产生业务效果；明确 ID 拒绝后的新尝试留有映射，结果不明不换 ID 重发，部分成功不重发成功项，切换式操作不因重试反转。普通同步自动更新当前副本并保留草稿及操作历史。

### 11.2 请求行为

5. 缓存新鲜期内连续查询不增加相关上游请求，包括已确认的空集合；并发冷查询共享一次任务，重复刷新遵守冷却和任务合并。读取不续期，局部写入不假定整域刚校验，无变化同步不重复重算。
6. 完成在途任务后观察至少 10 分钟，钱迹请求计数不增长，且没有周期性轮询或保活触发器。
7. 切换线路从 Worker 出口验证；连接变化不导致重复写入、游标错误或账单消失。
8. 服务和协调器重启后可恢复连接和任务；待核查写入不会因 alarm 重投递而再次发送。

### 11.3 页面、MCP 和真实上游

9. 同筛选条件下网页、MCP 的账单集合、分页和金额一致；桌面与手机浏览器可以完成主要流程。
10. MCP 初始化、工具发现、Schema、注解、错误及任务跟踪可用，ChatGPT 能通过实际 Cloudflare 入口调用。
11. 使用用户指定的专用测试账本和明确测试数据逐项验收写入；先检查回执，再回拉，再在官方客户端核对。
12. 资源管理、资产债务和高级计划等不属于测试账本的操作，采用明确命名的测试对象逐项核验影响；不以测试账本的普通账单成功替代这些验收。
13. 所有交付目标在能力清单中有证据、状态和验收结果。发布说明逐项列出确实不可用的上游能力及原因，不将模拟测试通过称为真实支持。
14. 通过两端先后修改、相同及不同字段交叉修改、编辑与删除交叉、离线修改后同步、受控的新建 ID 冲突和响应丢失实验，记录服务端实际仲裁结果；不用 `conf_ids` 的本地 ID 重分配行为代替这些证据。
15. 采用各域审查文档的边界向量验证金额及关系，至少覆盖优惠不重复扣、跨期退款、新旧报销、三币种保存值、两个独立排除标记、父子预算防重复、资产差额选项、借贷包装项、周期月末/调休、分期尾差/初始次数、储蓄撤销关联账单和官方图片 key。
16. 覆盖最终复核顺序用例：已发送待核查后触发同步不重写；不同UID不发旧操作；重建首/中/末页排队写入不被集合切换覆盖；旧缓存下的toggle及目标packId解绑不反向操作；只读重建可参与核查且不形成互相等待。
17. 以同一数据集测冷/热查询、首次同步、年度统计和在途任务的状态读取；记录入口/DO CPU及数据库读写计量。本地查询不因20秒网络等待被全局锁阻塞，统计不无界装载整库，付费与架构收益以实际测量说明。故障演练包含任务落库/安排续跑边界、对象重建及维护恢复不重放历史写入。
18. 覆盖缓存顺序向量：t=0校验、t=40读取、t=80仍需检查；t=50局部写不推迟t=65的全域检查；慢读晚于新写到达不覆盖；空结果不反复拉取；过期失败保留副本；源数据不变但跨业务日/周期时结果正确换键。Web显示缓存状态，MCP不把缓存冒充新验证结果。

| 图片链路 | 上传流程、资源引用及清理语义 | 图片写入不开放，不把链接字符串当成上传成功 |
| 退款/新旧报销及统计 | 已确认模型与本地公式对照官方数据；旧模型升级、超额和次数限制、空值清除、异常映射 | 实现已确认分支，标明未验证边界；不自动账号升级，不把缺失子记录当零 |
| 疑似 APK 缺陷与非活跃入口 | 提前还款 images 寄存器载荷、random 创建入口、resetCount 无直接调用者等 | 保留证据，核对正确契约；不盲抄疑似错误或凭名称开放能力 |

研究、协议适配、同步、领域业务、网页/MCP和上游验收按依赖组织成实施任务；不把尚未研究清楚的接口提前标为可用。已编制[开发计划](../plans/2026-10-18-qianji-development-plan.md)，用户已确认更新计划，采用主代理顺序实现与最终统一独立审查。
